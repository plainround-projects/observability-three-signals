# SQL

## What it is

SQL (Structured Query Language) is the language for asking a relational database for data and for changing it. Statements fall into groups: **DDL** (data definition: `CREATE TABLE`, `CREATE INDEX`, `GRANT`) describes the structure; **DML** (data manipulation: `INSERT`, `UPDATE`, `DELETE`, `TRUNCATE`) changes the rows; a **query** (`SELECT`) reads rows. A statement ends with a semicolon.

## Why this repository uses it

The data model is tiny but it is shaped for the lesson: an `orders` table, an `order_items` table with an index on `order_id` (so the lookup is an index scan, not a table scan), a read-only role, and seed data with a fixed distribution (200 orders of each size from one to five items) so every run produces the same rows. The slow query is plain SQL: the same statement with `pg_sleep(1.5)` in it.

## How it works underneath

The server parses the text, builds a **plan** (which tables to read, in which order, using which indexes), executes the plan and returns rows. `SELECT cols FROM table WHERE condition ORDER BY col` means: read rows from the table, keep those that satisfy the condition, sort them, return the listed columns. A `JOIN` combines rows of two tables; `CROSS JOIN` pairs every row of one with every row of the other (with a one-row source it adds columns without changing the row count). `GROUP BY` collapses rows with the same value into one row so that aggregate functions (`count(*)`, `sum`) can summarize them. `CASE WHEN ... THEN ... ELSE ... END` is an if/else inside a query.

A **parameter** in application code (`%(order_id)s`) is a placeholder. The program sends the statement text and the values separately, so the database never mistakes a value for SQL. This is what stops **SQL injection**.

Some lines in the files are not SQL but `psql` meta-commands: they start with a backslash (`\gexec`, `\timing`) and are handled by the client program. A `psql` variable (`-v name=value`) can be used in a script as `:name`, or as `:'name'` to insert it as a quoted string.

## Walkthrough of this repository's use

### `001_schema.sql`

```sql
-- 001_schema.sql: DDL for the orders database. Safe to run again.
-- Run with: make db   (psql variable reader_password comes from ORDERS_READER_PASSWORD)

CREATE TABLE IF NOT EXISTS orders (
    id            integer     PRIMARY KEY,
    customer_name text        NOT NULL,
    placed_at     timestamptz NOT NULL DEFAULT now()
);
```

The first two lines are SQL comments (`--` to the end of the line) that explain how to run the file. `CREATE TABLE IF NOT EXISTS orders (...)` creates the table only if it does not exist, which makes the file safe to run again. Columns: `id integer PRIMARY KEY` (unique, not null, indexed), `customer_name text NOT NULL`, and `placed_at timestamptz NOT NULL DEFAULT now()` (a time stamp with time zone, filled with the current time if not given).

```sql
COMMENT ON TABLE orders IS 'One row per order; the back service reads it with SELECT id, customer_name.';
```

`COMMENT ON TABLE ... IS '...'` stores a description in the database itself (shown by `\d+`).

```sql
CREATE TABLE IF NOT EXISTS order_items (
    id               bigint  GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    order_id         integer NOT NULL REFERENCES orders (id),
    sku              text    NOT NULL,
    quantity         integer NOT NULL CHECK (quantity > 0),
    unit_price_cents integer NOT NULL CHECK (unit_price_cents >= 0)
);
COMMENT ON TABLE order_items IS 'The lines of an order; 1 to 5 per order in the seed data.';
```

`order_items` has `id bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY` (a number that the database counts up by itself, but you may also give one), `order_id integer NOT NULL REFERENCES orders (id)` (a **foreign key**: the value must exist in `orders.id`, so there are no items without an order), `sku text`, `quantity integer NOT NULL CHECK (quantity > 0)` and `unit_price_cents integer NOT NULL CHECK (unit_price_cents >= 0)`. A `CHECK` is a rule the database enforces on every insert.

```sql
-- The back service looks items up by order id, so the lookup must be an index scan, never a table scan.
CREATE INDEX IF NOT EXISTS order_items_order_id_idx ON order_items (order_id);
```

The comment gives the reason for the index: the service looks items up by order id, and without an index the database would read the whole table for each request. `CREATE INDEX IF NOT EXISTS order_items_order_id_idx ON order_items (order_id)` builds a sorted structure on that column.

```sql
-- Least privilege: the back service connects as a role that can read these two tables and nothing else.
SELECT format('CREATE ROLE orders_reader LOGIN PASSWORD %L', :'reader_password')
WHERE NOT EXISTS (SELECT 1 FROM pg_roles WHERE rolname = 'orders_reader')
\gexec
SELECT format('ALTER ROLE orders_reader LOGIN PASSWORD %L', :'reader_password')
\gexec
```

The role. `SELECT format('CREATE ROLE orders_reader LOGIN PASSWORD %L', :'reader_password')` builds the text of a `CREATE ROLE` statement. `format` fills `%L` with its argument, quoted as a SQL literal. `:'reader_password'` is the `psql` variable set with `-v reader_password=...`, inserted as a quoted string. `WHERE NOT EXISTS (SELECT 1 FROM pg_roles WHERE rolname = 'orders_reader')` makes the query return a row only if the role does not exist yet. `\gexec` is a `psql` command (not SQL): it executes each value of the result as a statement. So the role is created once, with the password from the environment, and never appears in the file. The second `SELECT format('ALTER ROLE ...')` plus `\gexec` always updates the password, so changing `.env` and running `make db` again changes it.

```sql
GRANT CONNECT ON DATABASE orders TO orders_reader;
GRANT USAGE ON SCHEMA public TO orders_reader;
GRANT SELECT ON orders, order_items TO orders_reader;
```

The grants: `GRANT CONNECT ON DATABASE orders` lets the role connect; `GRANT USAGE ON SCHEMA public` lets it see objects in the default schema; `GRANT SELECT ON orders, order_items` lets it read the two tables. Nothing else, so an `INSERT`, `UPDATE` or `DELETE` fails with "permission denied".

### `002_seed.sql`

```sql
-- 002_seed.sql: DML. 1,000 orders with 1 to 5 items each (200 orders of each size); no randomness, so every
-- run produces the same rows. Replaces any earlier seed.

TRUNCATE order_items, orders RESTART IDENTITY CASCADE;
```

`TRUNCATE order_items, orders RESTART IDENTITY CASCADE` empties both tables, restarts the identity counter and also empties tables that depend on them. Running the seed twice gives the same result.

```sql
INSERT INTO orders (id, customer_name, placed_at)
SELECT n,
       'customer-' || lpad(n::text, 4, '0'),
       timestamptz '2026-10-01 08:00:00+00' + (n * interval '7 minutes')
FROM generate_series(1, 1000) AS n;
```

`INSERT INTO orders (...) SELECT ... FROM generate_series(1, 1000) AS n` inserts one row per number from 1 to 1000. `generate_series` is a function that returns a set of consecutive numbers. `'customer-' || lpad(n::text, 4, '0')` joins the text `customer-` with the number turned to text (`::text` is a cast) and padded with zeros to four characters: `customer-0003`. The time is a fixed start plus `n * interval '7 minutes'`, so no clock is used and the rows are always the same.

```sql
-- Order n gets 1 + (n * 7 mod 5) items: sizes 1 to 5, spread evenly.
INSERT INTO order_items (order_id, sku, quantity, unit_price_cents)
SELECT o.id,
       'SKU-' || lpad((((o.id * 13 + line * 7) % 50) + 1)::text, 3, '0'),
       1 + ((o.id + line) % 4),
       500 + ((o.id * 31 + line * 17) % 90) * 100
FROM orders AS o
CROSS JOIN LATERAL generate_series(1, 1 + (o.id * 7) % 5) AS line
ORDER BY o.id, line;
```

Items. The comment states the rule: order `n` gets `1 + (n * 7 mod 5)` items, so sizes 1 to 5 appear 200 times each. `CROSS JOIN LATERAL generate_series(1, 1 + (o.id * 7) % 5) AS line` makes one row per item number for each order (`LATERAL` lets the right side use the current row of the left). The columns are arithmetic on the ids with `%` (modulo, the remainder after division): the SKU is `SKU-` plus a number from 1 to 50, the quantity from 1 to 4 and the price from 500 to 9400 cents, all deterministic. `ORDER BY o.id, line` makes the insert order stable.

```sql
ANALYZE orders;
ANALYZE order_items;
```

`ANALYZE` refreshes the table statistics the query planner uses, so the first queries pick the index.

### `003_queries.sql`

```sql
-- 003_queries.sql: the queries the lesson runs. Run with: make queries

-- 1. The orders lookup the back service runs first: one row by primary key.
SELECT id, customer_name FROM orders WHERE id = 3;

-- 2. The order_items lookup it runs second (the planned fault delay is 0 here): the index on order_id answers it.
SELECT oi.id, oi.sku, oi.quantity, oi.unit_price_cents
FROM order_items AS oi CROSS JOIN pg_sleep(0) WHERE oi.order_id = 3 ORDER BY oi.id;
```

Queries 1 and 2 are the two statements the back service runs. The second contains `CROSS JOIN pg_sleep(0)`, a join with a function that returns after zero seconds.

```sql
-- 3. The same query with the planted fault: the database itself spends 1.5 seconds inside this one statement,
--    which is why the trace shows one SELECT span far wider than its siblings.
\timing on
SELECT oi.id, oi.sku, oi.quantity, oi.unit_price_cents
FROM order_items AS oi CROSS JOIN pg_sleep(1.5) WHERE oi.order_id = 3 ORDER BY oi.id;
\timing off
```

Query 3 is the planted fault: the same statement with `pg_sleep(1.5)`. `\timing on` and `\timing off` are `psql` commands that print how long each statement took. You will see about 1500 ms: this is the time the trace shows as one wide `SELECT` span.

```sql
-- 4. How many orders fall in each item-count bucket (the values of the order.item_count_bucket attribute).
SELECT CASE WHEN item_count <= 2 THEN '1-2' WHEN item_count <= 5 THEN '3-5' ELSE '6+' END AS bucket,
       count(*) AS orders
FROM (SELECT order_id, count(*) AS item_count FROM order_items GROUP BY order_id) AS sizes
GROUP BY 1 ORDER BY 1;

-- 5. Row counts after seeding: 1,000 orders and 3,000 items.
SELECT (SELECT count(*) FROM orders) AS orders, (SELECT count(*) FROM order_items) AS items;
```

Query 4 counts orders per item-count bucket. The inner query `SELECT order_id, count(*) AS item_count FROM order_items GROUP BY order_id` gives the size of each order; `CASE WHEN ... THEN ... END` maps it to the bucket text; `GROUP BY 1` groups by the first output column; `ORDER BY 1` sorts by it. Query 5 prints the row counts: 1,000 orders and 3,000 items.

## Try it yourself

```bash
make queries
```

Expected (needs `make up`): five result tables; query 3 prints `Time: 15xx.xxx ms`; query 4 shows buckets `1-2` (400 orders) and `3-5` (600 orders); query 5 shows `1000 | 3000`.

```bash
docker compose exec postgres psql -U postgres -d orders -c "EXPLAIN SELECT * FROM order_items WHERE order_id = 3"
```

Expected: a plan with `Index Scan` or `Bitmap Index Scan` on `order_items_order_id_idx`, not `Seq Scan`.

```bash
make db
```

Expected: no output and exit code 0; running it twice gives the same data.

```bash
docker compose exec postgres psql -U postgres -d orders -c "SELECT order_id, count(*) FROM order_items GROUP BY order_id ORDER BY order_id LIMIT 5"
```

Expected: orders 1 to 5 with counts 3, 5, 2, 4, 1.

## Mistakes people make

- **Building SQL by joining strings.** Use parameters.
- **`SELECT *`** in application code makes the program depend on the column order.
- **Forgetting `WHERE` on `UPDATE` or `DELETE`.**
- **Assuming rows come back in a stable order** without `ORDER BY`.
- **Not testing the seed file twice.** The seed here starts with `TRUNCATE` so it is repeatable.

## Check yourself

1. What is the difference between DDL and DML? *DDL defines structure; DML changes rows.*
2. What does `WHERE` do? *Keeps only the rows that satisfy a condition.*
3. What does `GROUP BY` do? *Collapses rows with equal values so aggregates can summarize them.*
4. Why pass values as parameters? *So values can never be read as SQL, preventing injection.*
5. What is `\gexec`? *A `psql` command that runs each result row of the previous query as SQL.*
