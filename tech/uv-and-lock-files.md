# uv, the lock files and pip-audit

## What it is

Two ideas that belong together: a **lock file** and a **vulnerability audit**.

A **lock file** lists every package the project needs, including the packages those packages need (the **transitive** dependencies), each at one exact version with the cryptographic hashes of the files that may be installed. Without it, `flask>=3.1` could install a different version next month and behave differently. `requirements.lock` and `requirements-dev.lock` in this repository are lock files in the `requirements.txt` format, generated by the tool `uv`. uv is a very fast Python package manager written in Rust; the command that made them is written at the top of each file.

`pip-audit` is a command that looks up each pinned package version in a database of known security vulnerabilities (the Python Packaging Advisory Database, PyPI's) and reports any that match.

## Why this repository uses it

A lesson is only repeatable if the same versions install every time. The two lock files fix the version and the hash of every package, including the ones the packages pull in. The Docker build and `make install` both install from them with hash checking, and `make audit` (also run in CI) checks the pins against known vulnerabilities.

## Where it appears

| Path | What it is |
| --- | --- |
| `requirements.lock` | Run-time dependencies (38 packages), used by the Dockerfile. |
| `requirements-dev.lock` | Run-time plus development tools (77 packages), used by `make install`. |
| `pyproject.toml` | The ranges the locks were solved from. |
| `Dockerfile` | `pip install --require-hashes -r requirements.lock`. |
| `Makefile` | `install` and `audit` targets. |
| `.github/workflows/ci.yml` | Runs `make audit`. |

## How it works underneath

`uv pip compile pyproject.toml --universal --generate-hashes --python-version 3.12 -o requirements.lock` reads the dependency ranges in `pyproject.toml`, solves for one set of versions that satisfies all of them, and writes each as `name==version` followed by `--hash=sha256:...` lines. `--universal` makes the result valid on every operating system (a package needed only on Windows is marked with an environment marker such as `; sys_platform == 'win32'`). The `# via flask` lines under each entry record why the package is present.

`pip install --require-hashes -r requirements.lock` makes pip refuse any file whose hash is not listed. That defends against a tampered or substituted package. In hash mode, pip also requires every package to be pinned exactly, so nothing unlisted can slip in.

`pip-audit --no-deps --disable-pip -r requirements-dev.lock` reads the pins from the file and queries the vulnerability service for each, without resolving or installing anything. A **CVE** or an advisory id in the report names a known flaw; the report lists the version that fixes it.

## Walkthrough of this repository's use

### The header of a lock file

The lock files are generated, so they are not read line by line; their structure is. The first two lines of `requirements.lock` are comments that record the command:

```text
# This file was autogenerated by uv via the following command:
#    uv pip compile pyproject.toml --universal --generate-hashes --python-version 3.12 -o requirements.lock
```

(The development lock is built the same way with `--extra dev` and a different output file.) Each package then looks like this:

```text
blinker==1.9.0 \
    --hash=sha256:b4ce2265a7abece45e7cc896e98dbebe6cead56bcf805a3d23136d145f5445bf \
    --hash=sha256:ba0efaa9080b619ff2f3459d1d500c57bddea4a6b424b60a91141db6fd2f08bc
    # via flask
```

`blinker==1.9.0` pins one exact version. Each `--hash=sha256:...` is the checksum of one downloadable file of that version (there can be several: one per operating system or Python version); pip accepts a file only if its hash is in this list. The backslashes continue the line. `# via flask` says why the package is there.

### How the files are used

```dockerfile
WORKDIR /app
COPY requirements.lock ./
RUN pip install --require-hashes -r requirements.lock
```

In the image, `pip install --require-hashes -r requirements.lock` installs exactly the locked set.

```makefile
$(STAMP): requirements-dev.lock pyproject.toml
	$(PYTHON) -m venv $(VENV)
	$(VENV)/bin/pip install -q --require-hashes -r requirements-dev.lock
	$(VENV)/bin/pip install -q --no-deps -e .
	touch $@
```

`make install` builds `.venv` from `requirements-dev.lock` the same way, then installs the project itself with `--no-deps` (the lock already contains everything).

```makefile
audit: $(STAMP) ## check the locked dependencies for known vulnerabilities
	$(VENV)/bin/pip-audit --no-deps --disable-pip -r requirements-dev.lock
```

`make audit` runs `pip-audit --no-deps --disable-pip -r requirements-dev.lock`. `--no-deps` stops it from resolving dependencies again (the lock is already complete) and `--disable-pip` stops it from creating a temporary environment; it simply reads the pins and asks the vulnerability database about each one.

### Regenerating the locks

When `pyproject.toml` changes, you re-run `uv pip compile` with the command in the header (install uv with `pipx install uv` or `brew install uv`), review the diff, run `make check` and `make audit`, and commit both.

## Try it yourself

```bash
head -4 requirements.lock
```

Expected: the autogenerated comment with the compile command and the first package.

```bash
grep -c '^[a-z]' requirements.lock requirements-dev.lock
```

Expected: `requirements.lock:38` and `requirements-dev.lock:77` (the number of pinned packages).

```bash
make audit
```

Expected: `No known vulnerabilities found` (needs internet; results can change as new advisories appear, in which case update the pin).

```bash
.venv/bin/pip install --require-hashes --dry-run flask==3.1.3 2>&1 | tail -2
```

Expected: pip refuses with a message that hashes are required for every requirement, which shows the mode is strict.

```bash
.venv/bin/pip list --format=freeze | grep -i -E "^(flask|waitress|requests|psycopg)=="
```

Expected: the versions that the lock file lists.

## Mistakes people make

- **Installing from ranges in production.** Builds then differ from day to day. Install from the lock.
- **Editing the lock by hand.** Re-generate it with the compile command.
- **Ignoring audit findings** because the build "still works". Update the pin and re-lock.
- **Locking only for your own operating system.** `--universal` avoids that.

## Check yourself

1. What is a transitive dependency? *A package needed by one of your dependencies, not listed by you.*
2. What does `--require-hashes` protect against? *Installing a file that differs from the one that was locked.*
3. What does the `# via flask` line mean? *The package is in the lock because Flask requires it.*
4. What does `pip-audit` compare the pins against? *A database of known vulnerabilities.*
5. Why must you regenerate the lock after changing `pyproject.toml`? *The lock records the solved versions; it does not follow edits automatically.*
